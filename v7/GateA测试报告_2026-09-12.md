**一句话结论：** 实验确实观察到个别场景对站位非常敏感，但 6 个场景里经验最优候选 `p*` 全都等于官方默认站位 `p_ref`，相对默认站位的提升为 0；相对最近/IK 基线虽有 25.83 个百分点的总体点估计提升，95% 区间却为 `[0, 60.00]` 个百分点，下界没有大于 0。按提案“headroom 小则停止”的规则，不应在当前任务、策略和站位定义上进入昂贵的世界模型训练。

## 1. 先说这个实验在问什么

Gate A 不是在测试世界模型，也不是在比较导航器。它只回答 SkillBasin 立项之前最基础的一个问题：

> 对同一个已经冻结、不再训练的操作策略，仅仅改变底盘开始操作时的位置和朝向，任务成功率是否会稳定地变化？而且这个变化是否超过“走得最近”或“几何上最容易够到”所能解释的部分？

如果答案是“否”，后续训练世界模型去找好站位就没有必要；如果答案是“是”，才有理由继续 Gate B/C。Gate A 因此是一个低成本的止损实验。

## 2. 理论背景：什么是 basin，什么是 pose headroom

把冻结策略记为 \(\pi\)，场景记为 \(e\)，底盘的平面位姿记为

\[
p=(x,y,\theta)\in SE(2).
\]

机器人从 \(p\) 开始后，策略会反复执行“看观测—出动作—环境变化—再看观测”的闭环。在场景 \(e\) 中，能让这个闭环最终成功的起点集合，就是该策略在该场景中的 basin。通俗说，它是“这个策略从哪些地方开工更可能做成”的地图。

对一个候选位姿 \(p\)，用 \(N\) 次仿真执行估计成功率：

\[
\hat S(e,p)=\frac{1}{N}\sum_{i=1}^{N}
\mathbf 1\{\text{第 }i\text{ 次 rollout 成功}\}.
\]

候选集合中搜索阶段表现最好的位姿为

\[
p^*(e)=\arg\max_{p\in\mathcal P_{\mathrm{valid}}}\hat S_{\mathrm{search}}(e,p).
\]

但不直接用“挑出它”的搜索数据证明它好，而是用新随机种子重新执行。主指标为：

\[
H_{\mathrm{geom}}(e)=
\hat S_{\mathrm{val}}(e,p^*)-
\max\{\hat S_{\mathrm{val}}(e,p_{\mathrm{near}}),
\hat S_{\mathrm{val}}(e,p_{\mathrm{IK}})\}.
\]

这个差值叫“相对最强简单几何基线的站位上限空间”。它比 \(p^*-p_{\mathrm{ref}}\) 更严格：后者只说默认站位不好，前者还要排除“离得近就行”和“IK 裕量大就行”。

## 4. 用到的数据、权重和场景

### 4.1 本次没有训练新模型

实验是纯评测。没有使用 Gate A rollout 反向训练策略，没有训练世界模型，也没有训练站位成功率预测器。候选过滤只使用地图、碰撞体、相机和机器人运动学。

### 4.2 冻结策略

- 策略家族：Mobi-π 公开 `bc_xfmr`。
- 任务 checkpoint：`TurnOnStove` 和 `TurnOnSinkFaucet`，均为 seed 1、`mg-300`、epoch 1000。
- 每个 checkpoint 大小：246,511,841 bytes。
- 主干：6 层、8 头、embedding 512 的 Transformer；打印的 GPT backbone 参数量为 18,906,112。
- 动作维度：12；执行时保留手臂/夹爪动作，把移动底盘相关通道置零，并在 MuJoCo 每步后将底盘恢复到候选位姿。
- 观测：左/右第三人称 RGB、腕部 RGB，以及底盘、末端、夹爪低维状态。
- 语言条件：使用 checkpoint 原配的 `openai/clip-vit-large-patch14` 文本编码器，每个场景读取环境实际指令。

### 4.3 场景分割

Mobi-π 代码的官方协议用 layout `0,2,3,5,6` 训练，用 `1,4,7,8,9` 测试。本次选用测试集中的 `1,4,7`，layout ID 与 style ID 保持相同，因而是布局/外观两方面都与训练布局分离的场景。环境元数据中的物体实例分割为 `B`。

每个“场景”在本报告中指固定的任务、layout/style 和任务初始状态。对一个场景比较不同站位时，会恢复同一份 MuJoCo 快照，以免对象初始摆放变化混入站位效应。

### 4.4 为什么选这两个任务

- `TurnOnStove`：要接触小旋钮并沿正确方向转动，对视角、末端接近方向和接触裕量敏感。
- `TurnOnSinkFaucet`：要接触水龙头把手并转到成功区间，同样具有小目标和方向性。

两者都是 Gate A 方案预先指定的高位姿敏感任务，不是看到结果后再挑出来的任务。

## 6. 候选位姿与参数：选什么，为什么

### 6.1 候选数量：32

32 是 Gate A 方案中一天 smoke test 的预先值。它能覆盖多个距离、方位和朝向，又不至于在问题尚未证明前消耗数千次 rollout。

### 6.2 目标点

- 炉灶任务：从当前任务指定的炉灶旋钮 joint 解析世界坐标。
- 水龙头任务：从 sink `handle_joint` 解析世界坐标。
- 只在 joint 解析失败时才使用 fixture 中心加高度的后备估计。

这比用整个炉灶或水槽的中心更准确，因为“最近”和 IK 应该围绕真正需要接触的部件定义。

### 6.3 分层环带采样

- 半径：0.65 m 到 1.35 m，间隔 0.10 m。
- 相对目标的方位角：每 15° 枚举。
- 机器人朝向：面向目标的方向上再加 `-30°,-15°,0°,15°,30°` 偏差。
- 先用地板边界和家具平面占用多边形过滤，并用机器人底盘半径做膨胀。
- 对剩余候选用固定 seed 打乱，取 31 个，再加入官方默认位姿作为第 0 号候选。

半径范围的直觉是：太近容易底盘碰家具，太远机械臂必然够不到。0.65–1.35 m 包含近距离、常规操作距离和 IK 边界，不会把 32 个宝贵名额浪费在厨房远端。

### 6.4 三个资格过滤器

1. **底盘碰撞**：传送到候选后检查 MuJoCo contact；普通候选出现底盘穿透/碰撞则排除。官方默认位姿始终作为必测基线，但会如实记录碰撞标记。
2. **目标可见**：将交互点投到左/右 agent-view 相机视锥，至少一台相机内可见才通过。同时记录到视锥边界的 margin。
3. **基本 IK**：使用 MuJoCo Jacobian 的阻尼最小二乘位置 IK，最多 80 次迭代，末端与交互点距离容差 0.08 m，求解后最小归一化关节限位裕量至少 0.05。

IK 在这里只是“明显够不到的不要浪费 rollout”的过滤器，不会替策略生成动作，也不是 oracle。通过 IK 仍可能因视角、接近方向、接触和策略分布偏移而失败。

### 6.5 搜索与验证参数

| 参数 | 值 | 原因 |
|---|---:|---|
| 每任务场景 | 3 | 选自官方 held-out 集的 1/4/7，用于 smoke 阶段的跨布局复现 |
| 候选数 | 32 | Gate A 方案的最小 smoke 规模 |
| 每候选搜索 rollout | 3 | 先粗略建图和选 \(p^*\)，避免在问题尚未成立时过度投入 |
| 每唯一基线验证 rollout | 20 | 新 seed 独立估计搜索后选中位姿的成功率 |
| 最大时域 | 500 步 | checkpoint 原始评测配置；成功时可提前结束 |
| 策略 seed | 1 | 与公开 checkpoint 对应 |
| 场景 seed | `1 + scene_id` | 固定、可重现，同一场景的位姿比较共用快照 |
| bootstrap 次数 | 20,000 | 给出 2.5%/97.5% 分位的 95% 区间，数值稳定且成本低 |

## 7. 四个站位是怎样定义的

- \(p_{\mathrm{ref}}\)：RoboCasa/Mobi-π 对当前任务和场景计算的官方默认机器人初始位姿。
- \(p_{\mathrm{near}}\)：在同时通过碰撞、可见和 IK 过滤的候选中，底盘中心到交互点平面距离最小者。
- \(p_{\mathrm{IK}}\)：在同一严格可行集合中，求解后最小归一化关节裕量最大者；同分时选更近者。
- \(p^*\)：对所有已执行候选按 3 次搜索成功率排序；同分时先选离默认位姿更近者，再按候选 ID 破同分。

\(p^*\) 是一个后验 oracle：它用了真实 simulator rollout 成败来选点，只能用于 Gate A 确认“站位还有多大可挖空间”，不是 SkillBasin 未来部署时的选点方法。

## 8. 整体实验流程

```text
加载官方 checkpoint 中的配置、观测形状、环境元数据和动作归一化统计
        ↓
创建指定 held-out layout/style 的 RoboCasa 任务
        ↓
重置一次并保存同一份 MuJoCo 场景快照
        ↓
解析旋钮/水龙头把手的真实交互点
        ↓
生成 32 个 SE(2) 候选（默认位姿 + 目标周围分层环带）
        ↓
对每个候选：恢复快照 → 传送底盘 → 碰撞/可见/IK 过滤
        ↓
对可行候选：再恢复快照 → 锁定底盘 → 冻结策略闭环执行最多 500 步
        ↓
每个候选用 3 次搜索 rollout 估计粗成功率，选定 p_ref / p_near / p_IK / p*
        ↓
对四个标签对应的“唯一物理位姿”各做 20 次新 seed 验证
        ↓
逐场景计算成功率、headroom 和几何相关性
        ↓
分层 bootstrap：先重采样场景，再在场景内重采样 rollout 成败
        ↓
按预先标准给出 Gate A 判断和扩展建议
```

## 9. 评测代码逻辑审查

### 9.1 checkpoint 加载

评测器直接从公开 checkpoint 读取 `model`、`config`、`shape_metadata`、`env_metadata` 和动作归一化统计。这些信息足以原样恢复评测策略，因此不必为评测重新打开数 GB 的训练 HDF5。不读训练数据是 I/O 优化，不是模型简化。

公开归档把归一化向量序列化为 Python list，而当前 RoboMimic 要求 NumPy array。评测器只做类型转换，不改变任何数值。

### 9.2 位姿是唯一自变量

对一个场景，所有候选共用同一快照。每次 rollout 之前的顺序是：恢复快照、写入候选位姿、清零底盘速度、`sim.forward()`、刷新帧堆叠观测。这样策略看到的第一帧真的对应新站位，不会混入传送前的旧画面。

### 9.3 闭环执行而非单步打分

每一步都是“当前真实仿真 RGB/状态 → 冻结策略 → 真实 MuJoCo 动力学”。成功由 RoboCasa 任务自带成功谓词判断，不是人工看视频打标，也不是用距离或 IK 分数代替。

### 9.4 选择偏差控制

如果从 32 个候选里挑搜索成功率最高的一个，然后仍报这 3 次的成功率，结果会因“挑最高”而偏乐观。本实验把这 3 次只当作选择集，最终表格主要报告新的 20 次验证结果。

另外，如果一个物理位姿同时是 \(p_{\mathrm{near}}\)、\(p_{\mathrm{IK}}\) 和 \(p^*\)，它在验证时只执行 20 次，不会为三个名字各跑 20 次。Bootstrap 也对这一物理位姿只重采样一次，因此不会在本来完全相同的基线之间制造虚假差异。

### 9.5 几何解释诊断

对严格可行且已执行的候选，计算搜索成功率与以下三个量的 Spearman 秩相关：

- 负的目标距离（数值越大代表越近）；
- IK 关节裕量；
- 目标在双 agent-view 视锥中的可见 margin。

这三个相关性不能单独证明因果，但可以诊断高成功区是否几乎完全被简单几何排序解释。

| Faucet | 7 | 100% | 100% | 100% | 100% | 0 pp | 0 pp | 四者均为 0 |
| Stove | 1 | 100% | 0% | 0% | 100% | 0 pp | +100 pp | ref/star=0；near=19；IK=21 |
| Stove | 4 | 0% | 0% | 0% | 0% | 0 pp | 0 pp | 四者均为 0 |
| Stove | 7 | 0% | 0% | 0% | 0% | 0 pp | 0 pp | ref/near/star=0；IK=21 |

最关键的结构不是“某两格差得很大”，而是 **每一行的 `p*` 都与 `p_ref` 是同一个候选 0**。也就是说，离线 oracle 没在 32 个候选中找到比官方默认站位更好的点。

### 10.4 95% 区间

95% 区间用 20,000 次分层 bootstrap 得到：先重采样场景，再在场景内重采样每个物理位姿的 Bernoulli 成败。同一物理位姿具有多个标签时只重采样一次，保持标签间的配对关系。

| 范围 | `p_ref` CI | `p*` CI | `p* − p_ref` CI | `p* − max(near, IK)` CI |
|---|---:|---:|---:|---:|
| Faucet | [61.67%, 100%] | [61.67%, 100%] | [0, 0] pp | [0, 53.33] pp |
| Stove | [0, 100%] | [0, 100%] | [0, 0] pp | [0, 100] pp |
| 总体 | [24.17%, 94.17%] | [24.17%, 94.17%] | [0, 0] pp | [0, 60.00] pp |

所有任务的几何 headroom 区间下界都是 0；满足“下界大于 0”的任务数为 **0**，而预设要求至少 2 个。区间很宽并不是程序不稳定，而是只有 3 个场景/任务，且效果集中在单个场景。它诚实地表达了跨场景证据不足。

## 11. 结果的通俗解释

可以把实验想成：同一个“手艺不变”的机器人，被放到厨房目标周围 32 个开工位置；先让它每处试 3 次，找出看起来最好的位置，再换 20 组新随机种子复考。

结果有两层含义：

1. **站位确实会影响策略。** 在 Faucet scene 1，默认位置成功 12/20，而最近/IK 点只有 1/20；在 Stove scene 1，默认位置 20/20，最近点和 IK 点都是 0/20。这说明策略并非只要“够得着、看得见、站得近”就会做，它还依赖训练中熟悉的观察构图和接触轨迹。
2. **但没有发现默认位置之外的可开发上限。** 6 个场景里 oracle 最终都选回默认位置。两个 Faucet 场景默认位置已经 20/20，两个 Stove 场景则连 oracle 也 0/20。前者没有提升空间，后者更像策略本身不会该场景，而不是选站位就能救回来。

因此，`+25.83 pp` 不能解释成“SkillBasin 能提高 25.83 个百分点”。那只是 oracle/默认点相对两个较差的简单几何基线的差，而未来系统并没有击败默认点；其跨场景区间下界又是 0。实验支持的是“策略有站位偏好”，不支持“学习一个世界模型能找到比现有默认位置更好的站位”。

## 12. Gate A 判断

预先约定的通过逻辑是：

1. 至少两个任务中，\(p^*\) 比较强的 \(p_{\mathrm{near}}/p_{\mathrm{IK}}\) 有稳定提升；
2. 该提升的 95% 区间下界大于 0；
3. \(p^*\) 本身不能几乎全失败，否则说明是策略不会任务，而不是站位问题；
4. 高成功区不能只是“最近”或“IK 裕量最大”区域的另一种画法。

**判断：No-Go，Gate A 未通过。**

| 预设条件 | 观测 | 判定 |
|---|---|---|
| 至少 2 个任务有稳定的几何 headroom | 两任务点估计为正，但两者 CI 下界均为 0；满足任务数 0 | 不满足 |
| 95% CI 下界 > 0 | Faucet `[0,53.33]` pp，Stove `[0,100]` pp | 不满足 |
| `p*` 不能普遍很弱 | Faucet 较强；Stove 两个场景 oracle 0% | 部分满足 |
| basin 不能只是几何启发式 | 两个场景有反例，但没有跨场景稳定性 | 证据不足 |
| oracle 相对默认位置有可开发空间 | 6/6 场景 `p* = p_ref`，差值精确为 0 | 不满足 |

这里特意同时报告两个“headroom”口径，因为提案叙述同时关心“oracle 对默认/最近站位”与“oracle 对最强简单几何基线”。按较宽松的几何口径，点估计为正但不显著；按更直接的默认站位口径，提升就是 0。两种口径都不能通过 Gate A。

本次是有独立验证的强化 smoke test，而不是方案规定的 3 任务×8 场景正式实验。因此严格表述是：**没有获得进入正式 Gate A 或世界模型训练的支持性信号**；不能反过来宣称所有任务上永远不存在站位优化空间。

## 13. 局限、不能过度解读的地方和下一步

1. **规模仍是强化 smoke test。** 两任务、每任务三场景足以识别明显的站位效应，但不足以代替方案规定的 3 任务×8 场景正式门槛。
2. **\(p_{\mathrm{ref}}\) 是官方默认位姿代理。** 它与 Mobi-π/RoboCasa 的任务初始逻辑一致，但本次没有从训练 demonstration 统计目标相对位姿分布。正式版应两者同时报告。
3. **候选集是离散上界。** \(p^*\) 只是 32 个候选中的最优，不是连续 \(SE(2)\) 上的数学全局最优。
4. **搜索每点只有 3 次。** 独立 20 次可以诚实评估选中点，但搜索本身可能错过真正较好的位姿。正式版应用 5 次搜索并给 top-3 补试。
5. **一个 policy seed。** 结果反映这两个公开 seed-1 策略，还不能支持“所有同架构策略都如此”。
6. **仿真真值不等于真机。** Gate A 本来就是用 simulator 低成本确认问题，本报告不对真机成功率作外推。
7. **几何过滤器本身有近似。** 可见性检查的是目标点是否进入视锥，不是完整的像素级遮挡比例；IK 只解位置，不解决完整的末端姿态和接触路径。这也是它们只能当“便宜筛子”和简单基线的原因。

按照提案的止损原则，建议先停止当前配置下的世界模型训练。若仍希望救活方向，应先修改问题设定，再重新做 Gate A，而不是直接扩大模型：

1. 明确部署时为什么拿不到或不能使用 `p_ref`。如果真实问题是“从任意导航终点恢复到策略熟悉的默认相对位姿”，目标应重写为**复现策略熟悉站位**，而不是声称发现了优于默认的站位。
2. 从训练 demonstrations 直接统计目标相对底盘位姿，构造真正的 `p_ref` 分布；本次只用了官方环境默认位姿代理。
3. 若修改假设后仍继续，再执行正式协议：加入 `TurnOnMicrowave` 或控制任务，扩到 3 任务×8 场景×48 候选×5 搜索，并对 top-3 各补 15 次；正式方案还需要补齐 held-out scene 实例的定义，因为官方代码只有 5 个 held-out layout ID。
4. 加入多个 policy seed，并验证搜索阶段并列第一的候选。Faucet scene 1 的 candidate 26 与 candidate 0 搜索时同为 1/3，但按预设 tie-break 只验证了 candidate 0；正式实验应检验并列赢家是否稳健。
5. 若要研究“超越几何”的部分，把点可见性升级为像素遮挡率，把位置 IK 升级为带末端姿态和接触方向的 6D IK；否则几何基线可能过弱。

这些建议不是对失败结果的事后包装：核心决策仍是 No-Go。只有问题定义被改写且新的预注册通过条件明确后，才值得追加算力。
